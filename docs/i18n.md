# Languages and currency

The interface ships in **English** (default) and **Spanish**, and any other language can be added without touching components. The default currency is **USD** and every installation can change it. Nothing here needs an external i18n library: the system is small, typed and covered by tests.

| | Default | Where to change it |
| --- | --- | --- |
| Interface language | `en` (English), with `es` (Spanish) available | `i18n.defaultLocale` / `i18n.locales` in [`src/template.config.ts`](../src/template.config.ts) |
| Currency | `USD` | `currency` and `currencies` in the same file |
| Number and date format | `en-US` for English, `es-419` for Spanish | `locale` (regional format of the default language) |

## How the language is chosen

1. The `NEXT_LOCALE` cookie, set when a person picks a language in the selector (top bar and the sign-in, onboarding, consent and connections screens). It stores only a language code, lasts one year and is not a credential.
2. The browser's `Accept-Language` header, in quality order. A regional tag such as `es-PY` matches the `es` dictionary.
3. The installation default (`i18n.defaultLocale`).

Only codes listed in `i18n.locales` can be selected; a tampered or unknown cookie falls back silently. There is **no `/es/...` path prefix**: the OAuth sign-in, consent and onboarding paths are part of the MCP contract and external clients hold them, so the language travels in the cookie instead. The root layout reads it per request, so pages are rendered dynamically, which is expected for an authenticated application.

Switching language re-renders the server layout (`router.refresh()`), so open forms keep their state and no data is refetched.

## Configure an installation

```bash
# English, USD (the defaults)
npm run configure -- --name "My store"

# Spanish by default, Paraguayan format, guaraní as the default currency
npm run configure -- --default-locale es --locale es-PY --currency PYG

# Offer only English and Spanish; the product form lists USD, EUR and MXN
npm run configure -- --locales en,es --currencies USD,EUR,MXN
```

The script validates before writing: currency codes must be three-letter ISO 4217 codes known to Node's `Intl`, the default currency is always part of the list, every language must exist in `src/i18n/messages`, and `locale` must use the default language (`es-PY` needs `--default-locale es`; the script infers it when it can). `npm run doctor` repeats the check (`localization.config`).

**Currency details**

- Amounts are stored as integer minor units per product, together with the product's own currency. USD uses two digits, PYG and JPY none, KWD three; the digits come from `Intl`, never from a hard-coded `× 100`.
- The default currency is used for new products, the dashboard headline and the "Default currency" setting. The product form offers the codes in `currencies`; each product can use a different one, a sale cannot mix currencies, and revenue is reported separately per currency.
- **Changing the configured currency does not convert existing prices.** Existing products keep the currency they were saved with. There is no automatic exchange-rate conversion.
- The default is a build-time installation setting, like the brand. A per-business default currency would need a schema change and is not part of this version.
- `DEMO_LOCALE` (optional, `npm run demo:setup`) selects the language of the sample catalog; the demo uses the configured currency.

## Add a language

Example: French.

1. **Dictionary.** Create `src/i18n/messages/fr.ts`. Type it as `Messages`, so the compiler rejects missing or extra keys:

   ```ts
   import type { Messages } from '../types';

   const fr: Messages = {
     common: { close: 'Fermer', /* … every key of en.ts … */ },
     pos: { units: { one: '{count} unité', other: '{count} unités' }, /* … */ },
   };
   export default fr;
   ```

   Copy `en.ts` as the starting point. Keep the `{placeholders}` exactly; translate everything else.
2. **Register it.** Add `fr: { label: 'Français', intl: 'fr-FR' }` to `src/i18n/locales.ts` and a loader to `src/i18n/messages/index.ts` (the `Record<Locale, …>` type fails to compile if you forget).
3. **Enable it.** `npm run configure -- --locales en,es,fr`.
4. **Verify.** `npm test` compares your file with English: same keys, same placeholders, valid plural categories, no markup, every MCP scope and server error code translated. Then `npm run test:e2e`.
5. **Optional.** Add French names to `src/db/demo-catalog.ts` (without them the demo catalog falls back to English) and a README translation.

Languages with several plural forms (for example Russian `one`, `few`, `many`, `other`) provide those keys in the plural tables; `other` is mandatory and is the fallback.

## Writing messages

- Plain text with `{name}` placeholders. React escapes the result; **never put HTML in a message**. Split a message that needs a line break into two keys.
- Counts use plural tables: `units: { one: '{count} unit', other: '{count} units' }` and `t('pos.units', { count })`. A numeric parameter is formatted with the active language's digits and separators.
- Keys are stable identifiers (`area.name`). Add a key to `en.ts` first; `Messages` then forces every other language to provide it. A missing translation at runtime falls back to English, then to the key, so a gap never breaks a screen.
- Keep the tone of the language consistent. The bundled Spanish uses the rioplatense "vos" register of the original reference interface; add `es-MX`-style variants as separate languages if a customer needs a different register.

## Using it in code

| Where | How |
| --- | --- |
| Client component | `const { t, money, date, locale } = useI18n()` from `@/i18n/provider` |
| Server component, `generateMetadata` | `const { t, locale } = await getI18n()` from `@/i18n/server` |
| API error shown to a person | `describeError(error, t)` from `@/lib/api-client` |
| Money | `money(minorUnits, currency?)`; parse user input with `parseMoney`, round-trip with `moneyInput` |

Rules: no user-visible string literals in components (a test fails on Spanish leftovers); use `money()`/`date()` instead of `Intl` calls; pass raw failures to `describeError` so the text follows the language.

## What is intentionally not translated

- **API, MCP and logs stay in English.** Responses carry a stable `code` (for example `ORDERS_PAUSED`) and an English `message`. The interface translates by code (`errors.<CODE>`), and falls back to the server message for codes it does not know. Agents and operators therefore get one canonical vocabulary.
- **Business data**: product names, categories, descriptions, tenant notices and business names belong to the business, not to the interface.
- **Brand name** (`name` in the config). The tagline is translated unless `description` is set, which overrides it in every language.
- **Technical guides.** The top-level READMEs and changelogs are bilingual; other guides keep the language shown in the [documentation index](README.md).
- **Right-to-left layouts** are not implemented. The dictionary system supports such languages, but the stylesheet has not been reviewed for RTL, so do not claim support without that work.

- `tests/i18n.test.ts`: dictionary parity and placeholders, plural rules, fallback chain, hostile `Accept-Language`/cookie input, money formatting and parsing, configuration validation, the `configure` script's success and refusal paths, error translation by code, demo catalog currency scaling.
